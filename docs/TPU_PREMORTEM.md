# TPU pre-training: pre-mortem review (track D2, 2026-10-11)

Scope: `tpu/forge_jax.py` (data, checkpoints, resume, main loop, watchdog, pin), `cloud/kaggle_tpu_train.py`, `cloud/kaggle_tpu_sft.py`, `tools/tpu_arrival.sh`, `cloud/tpu_settings/*.json`. Not touched on purpose (another branch works on them): `apply_update`, `build_train_step`, `--muon-shard`, `tpu/bench_step.py`.
Every finding that could be reproduced on the CPU has a check in `tpu/test_premortem.py` (`JAX_PLATFORMS=cpu python test_premortem.py` from `tpu/`, about 3 minutes; the older suites `test_forge_jax.py` and `test_cool_blend.py` pass unchanged except that `test_cool_blend.py` now uses `--vocab 4400`, see F6).
Severity: BUG = wrong result or a wasted session that happens without a special cause; RISK = needs an unlucky event or a bigger model; OK = checked, nothing to do.

## Capacity of the data-parallel layout (v5e, 16 GiB = 17.2 GB per chip, about 16 GB usable)

Method: `build_train_step` (Muon, bf16, remat, 2048 tokens, vocab 32768, value embeddings in 8 layers) compiled for 8 fake CPU devices with abstract inputs and `memory_analysis()` (arguments, outputs, donated alias, temporaries per device). It is the CPU compiler's buffer assignment with XLA attention (no splash kernel, which keeps the scores of one layer, 268 MB per sequence for 16 heads, out of HBM), not a TPU measurement: read it as a conservative proxy. Peak = arguments + outputs - donated + temporaries. Script: `tpu/capacity_estimate.py MODEL MICRO` (`micro` = sequences per chip per micro-step; the optimizer step is `accum = 32 / (8 x micro)` micro-steps).

| model | parameters | 12 N state | micro 1 | micro 2 | micro 4 | verdict (16 GB) |
|---|---|---|---|---|---|---|
| 150M (30 x 576, ve 8) | 175 M | 2.1 GB | 4.6 GB | 6.2 GB | 9.6 GB | fits at micro 4 (and 8 probably) |
| 365M (24 x 1024, ve 8) | 365 M | 4.4 GB | 8.8 GB | 10.7 GB | 16.1 GB | micro 2 safe; micro 4 borderline on this estimate (the TPU run of 2026-10-11 used the first micro of `[4, 2, 1]`; its log line `--micro` says which; splash attention lowers the temporaries) |
| 365M without remat | 365 M | 4.4 GB | 24.7 GB | - | - | does not fit: keep remat |
| 600M (28 x 1280, ve 8) | 586 M | 7.0 GB | 14.0 GB | 16.4 GB | 23.9 GB | micro 1 only, no margin; 32 sequences per step then run as 4 micro-steps of 8 |
| 1B (32 x 1664, ve 8) | 988 M | 11.9 GB | 23.1 GB | 26.6 GB | - | does not fit at any micro |

Fit of the temporaries: about 7.8 bytes x N fixed (accumulated gradients plus the update's stacked Muon copies) plus 1.9 GB (365M), 2.4 GB (600M), 3.5 GB (1B) per sequence per chip, so the replicated layout ends near 0.65 B parameters at micro 1, and the checkpoint files end at 555 M parameters (F2), whichever comes first. Above that the state must be sharded (the `--muon-shard` branch, or a sharded Adam state) and the pre-decay file dropped.

Checkpoint sizes: `ckpt_latest.bin` 12 N (365M: 4.4 GB; 600M: 7.0 GB; 1B: 11.9 GB), host RAM during a write is now one array (the largest is a 32768-row table, 25 to 55 MB), during a load 4 N for the read buffer plus the same on device 0 (R6).

## What changed in the code

`tpu/forge_jax.py`: `_shrink_time_limit` (F3); `save_checkpoint` streams one array at a time (F11); `tree_finite`, `out_space_needed`, `check_complete`, `validate_shards`, `CoolPool(min_len=)`, `--no-preflight`; in `main`: batch-geometry warning (F4), disk and data preflight (F2, F5, F6), stale `.tmp` removal (F8), non-finite stop with exit code 98 (F1), `safe_save` with exit code 96 for a failed final write (F2), a tests-only hook `FORGE_TEST_POISON_AT_STEP`. Exit codes: 2 = start-up check failed, 96 = final checkpoint not written, 97 = watchdog, 98 = non-finite. Format `forgeckpt1`, numerics, defaults and the functions of the other branch are unchanged.
`cloud/kaggle_tpu_train.py`: `ckpt_complete`, `decay_unfinished`, stop on a broken previous checkpoint, log reset for a retry from step 0, `.tmp` cleanup, second line of `exit.txt`. `cloud/kaggle_tpu_sft.py`: `decay_unfinished` in `summary.json`.

## Update 2026-10-11 night (branch loop2): what the logs of the 365M session showed about R2 and R3

`tools/session_breakdown.py` on the logs of that session (28,176 s in the trainer): a normal checkpoint write took 9.9 s (7 to 13 s), not 25 s; two writes took 351 s and 237 s (R2's "worst stall", and one more), and the loop itself stood still for 332 to 356 s three times, each time 80 steps (30 s) after a 4.4 GB write: together 1,623 s = 5.8 % of the trainer's time, against 0.6 % for all normal writes. The notebook output froze for 105 to 241 s five more times (the runner's own writes blocked; lines released in a burst), which the trainer's clock does not show. The trainer's silence limit (R3) was never near: no stall was longer than 359 s. New options, all off by default: `--async-io` (log.jsonl and the periodic checkpoints written by background threads, forced to the disk in pieces of 256 MB), `--async-steps N` (pipelined steps), `--stall-trace-s` (on by default: the stack of every thread once per stall), `--eval-early-until`; details and the table in the research note "ForgeInfer - TPU Compile Lab". A half-written file still never replaces a good one: the thread writes `<name>.tmp`, syncs it and renames it; two writers never share a file; the pre-decay and the last checkpoint are written before the run ends (a failed last one is exit code 96 as before).
