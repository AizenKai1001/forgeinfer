## Forge Studio and ForgeInfer v0.1.1 (pre-release)

Faster long prompts on NVIDIA Ampere and Ada cards, a progress bar while a long prompt is read, a fix for long contexts on dense models, and measurements of what the integer prompt GEMMs cost in quality at long context.

**Prompt speed (compute capability 8.0 and newer)**
- New prompt-attention kernels (`flash_a80.cu`): `m16n8k16` tensor-core MMAs, a double-buffered cp.async pipeline for the key and value tiles, no mask on tiles below the diagonal. Qwen3.5's 256-wide gated attention runs as warp pairs that share the score matrix (no recomputation) in swizzled shared memory: 1.9 times faster than the old kernel with bit-identical results; the dense head widths 64 and 128 are 1.3 to 1.5 times faster (bit-identical at 128).
- Gated DeltaNet prompt kernels (Qwen3.5): the scan keeps several state columns per thread (it was limited by shared-memory traffic) and the prep kernel handles 8 tokens per block; bit-identical, the scan takes 740 instead of 1,230 microseconds per layer.
- The feed-forward layer's SwiGLU and the int8 quantization of the down projection's input run as one kernel (bit-identical, 1.6 percent of a prompt pass).
- Qwen3.5-4B on an RTX 4060, 16,000-token prompt: 3,245 to 3,871 tokens/s (+19 percent, one measurement window). Same hour against llama.cpp b11517 (`llama-bench -p N -n 0`): +28 percent at 4,096 tokens, +29 percent at 16,384, +14 percent at 32,768, +5 percent at 65,536; the 9B at 16,384 tokens +22 percent.
- Dense models no longer fail to start with `CUDA_ERROR_INVALID_VALUE` at contexts beyond about 11,000 positions: the decode attention is split over the context and merged exactly. A needle-in-a-haystack check passes up to 129,000 tokens on an 8 GB card (4B with `--kv int8`).

**Prompt progress**
- A streamed request with `"return_progress": true` (llama.cpp's field) gets chunks with `prompt_progress` {total, cache, processed, time_ms} while a long prompt is read, one after every 1,024 tokens and before the first token. Forge Studio shows "Reading the prompt: 13,288 of 27,000 tokens (49 %), about 3 s left" with a bar, the chat page shows the same line, and `tools/progress_check.py` tests it against a real engine. Closing the connection during a long prompt frees the engine within one piece (`tools/cancel_check.py`).

**Quality at long context (measured, nothing changed by default)**
- The integer prompt GEMMs quantize activations to int8 (one scale per 32 values, as llama.cpp does). On the Qwen3.5-4B they cost a KL of 0.0152 against the fp16 path at 16,000 tokens of text (0.0010 at 512), about 1 percent of perplexity; the same shows with the single-token decode kernels on a second GPU, so it comes from the int8 activations, not from the new kernels. It is carried by about 1 percent of the positions (confident choices between near-equivalent earlier lines), and a multi-fact retrieval test (`tools/retrieval_check.py`) finds every code with and without it. Details and the emulation table (an asymmetric range with a zero point would cut the KL by four) are in `docs/PERFORMANCE.md`.
- Study switches, all off by default: `FORGE_FAKEQ` (quantize and dequantize activations in place before the fp16 GEMM, on any GPU), `FORGE_MMQ_SKIP` and `FORGE_MMQ_SKIP_FROM` (keep chosen matrices out of the integer path; the DeltaNet output projection alone carries three quarters of the loss for 2.6 percent of the prompt speed).

**Tools**: `tools/needle_check.py`, `tools/retrieval_check.py`, `tools/cancel_check.py`, `tools/progress_check.py`.

Unsigned binaries. Studio has been run on Windows 11 with an RTX 4060 and on Ubuntu 24.04 (X11) with an RTX 2060 SUPER; the macOS build is compiled and unit-tested by CI but nobody has run its window yet.
