Settings of the Kaggle TPU kernel (`cloud/kaggle_tpu_train.py`): copy one of these files to `<dev>\kaggle\stage\forge-tpujob\settings.json` and publish the dataset
(`cd <dev>/kaggle/stage/forge-tpujob && bash <dev>/kaggle/kg.sh datasets version -p . -m "text"`; a `-p X:/...` path fails on Kaggle's upload cache) before the user starts the run from the Kaggle page.
- v1_recipe_150M: the recipe of the homelab run f1_v1 (45,000 steps of 65,536 tokens = 2.95 B tokens).
- v2_ve8_150M: value embeddings in 8 of 30 layers with a 100x table rate (proxy: -0.134 against -0.063 for v1's 4 layers at 20x).
- m365_ve8: a 365 M-parameter model (24 layers, d 1024, 16/4 heads, ffn 4096, value embeddings in 8 layers), 100,000 steps = 6.5 B tokens: about 7 hours on a v5e-8 if it reaches 35 % of the peak; only after the first TPU session has shown the real speed.

- m365_ve8_auto: the recipe of m365_ve8 with the in-session autotune (`cloud/kaggle_tpu_train.py`, setting `autotune`) and the trainer taken from the small dataset `forge-jax-code` (`code_dataset`; `@ds:forge-jax` in the arguments is the folder of that input dataset, here for the cool-down shards). At the start of the session the candidates (the speed options that compute the same function: `--muon-shard`, `--attn-prep lane`, `--muon-lean --ns-barrier`, `--remat-policy dots+attn`, ...) are benchmarked against `base` on the session's own TPU (about 10 to 20 minutes), the fastest one that agrees on the first-step loss and is at least 2 percent faster is added to the trainer's flags; a failure keeps the plain settings. `forge-jax-code` must hold `forge_jax.py` AND `bench_step.py` of the same version. The compiler's estimates of the 365M step (compile lab, 2026-10-11): base 365 ms, lane + muon-shard 238 ms, + muon-lean + ns-barrier 220 ms; the TPU decides. `--steps 100000` caps the plan (6.5 B tokens of data): with a faster step the schedule ends earlier than the 28,000 s limit; raise it only together with more data.

**Host-side options of the 365M settings (2026-10-11 night, branch loop2; none of them is measured on a TPU).** The accounting of the 28,176 s of the first 365M session (`tools/session_breakdown.py`, research note "ForgeInfer - TPU Compile Lab", section "Where the 365M session went") shows 92.3 % in the steps, 0.6 % evaluations, 0.6 % normal checkpoint writes, 0.7 % start-up and 5.8 % in five stalls of 4 to 6 minutes (two slow checkpoint writes, three stops of the loop outside the step, all within 80 steps to 1,000 steps after a 4.4 GB checkpoint write), while the host's own work between two steps is 0.09 ms. Both files: `--eval-every 250 --eval-early-until 1000` (an evaluation every 100 steps for the first 1,000 steps, then every 250: 280 instead of 685 evaluations, about 100 s). `m365_ve8_auto.json` only: `--async-steps 2` (the loss of a step is read two steps late, so that the device never waits for the host's bookkeeping or the dispatch of the next step; the numbers, checkpoints and printed lines are byte-identical on the CPU tests; the first step, evaluations, checkpoints and the end of the run empty the pipeline; a NaN is found two steps later) and `--async-io` (log.jsonl and the periodic checkpoints are written by background threads, the checkpoint is forced to the disk in pieces of 256 MB so that no 4.4 GB of dirty pages pile up; the pre-decay and the last checkpoint are written before the run ends; a periodic checkpoint is skipped when the previous write is still running). The autotune's attention pick (`attn_pick` in bench.json) is handed to the trainer as `--attn-pick`, which skips its own 2-minute self-test of the splash kernels. Take the two `--async-*` flags out of the arguments to get the loop of the first session.

The trainer (`tpu/forge_jax.py`) now plans its own number of steps whenever `--time-limit-s` is set (the learning-rate decay always ends inside the limit; `--no-auto-steps` turns that off), picks its attention on a TPU (`--attn auto|xla|splash`: a splash-attention Pallas kernel after an on-chip check against XLA's attention, XLA's otherwise, and a restart with XLA's if the kernel fails inside the full step), and reads the shards once in the background at the start (`--no-warm-data` to skip). Old and new settings files work with old and new trainers.

**Chat fine-tunes on the free TPU (`cloud/kaggle_tpu_sft.py`, settings `sft365_grid.json`).** The same JAX trainer fine-tunes a finished base on the chat shards (loss mask in bit 15, validation tail of the last shard; checked on 2026-10-11 against the Rust trainer: the same masked validation loss 0.4579 on the same windows from the same weights). One Kaggle session runs the listed runs one after the other (a learning-rate grid for one session start), cuts every finished checkpoint down to the weights (header + parameters: 1.46 GB for the 365M model instead of 4.4 GB) and writes `summary.json`. Datasets: `forge-sft365` (the six shards, uploaded 2026-10-11), `forge-base365` (the cut base checkpoint: make it from `ckpt_latest_params.bin` of `tools/tpu_arrival.sh`, file name `ckpt_latest.bin`), `forge-tpujob-sft` (settings.json), `forge-jax` (the trainer). Kernel folder `<dev>/kaggle/stage/forge-tpu-sft-kernel` (`kernels push -p .`, then the session is started from the Kaggle page with the accelerator set to TPU, like the pre-training kernel). Set `max_s` and `--steps` of every run from the measured tokens per second of the base's pre-training log (the grid has 3 runs of 2,300 steps = 150 M tokens each).

**Step benchmark: one short TPU session that says which speed option pays (`cloud/kaggle_tpu_bench.py` + `tpu/bench_step.py`).** The trainer has options that may make the 365M step faster on the free v5e-8 but have never run on a TPU: `--muon-shard` (each chip orthogonalises its share of the stacked Muon matrices instead of all eight doing all of them), `--no-remat`, `--micro 8`, and the LIBTPU async-collective flags (marked unverified on this libtpu). Nothing about their speed is known until this session has run; all of them default to OFF in the trainer.
- Set-up (once): put `bench_step.py` next to `forge_jax.py` in the root of the dataset `forge-jax` (both files are needed; publish a new dataset version the way `forge_jax.py` is published). A kernel named `forge-tpu-bench` with `cloud/kaggle_tpu_bench.py` as its script and the dataset `forge-jax` attached (no data dataset, no `forge-tpujob`; the optional dataset `forge-tpujob-bench` holds a `settings.json` with any of `args`, `only`, `total_s`, `per_variant_s`, `jax_pin`, `require_accelerator`). Push it like the training kernel (`kernels push -p .`).
- Start: the same UI steps as the training kernel: open the kernel on the Kaggle page, set the accelerator to TPU v5e-8 in the editor, confirm it, then run it (a push alone does not start a TPU session). It stops by itself after at most 25 minutes (`total_s` 1500, the JAX installation included); a variant that cannot finish before that is skipped, one that hangs is killed after 420 s.
- Each variant runs in its own process (an OOM or a flag the runtime rejects only fails that row): base, muon-shard, window512, muon-shard+window512, remat-attn, fuse-qkv, hd128, all, no-remat, no-remat+muon-shard, micro8, micro8+no-remat, libtpu-async, muon-shard+libtpu-async (the unlikely-to-fit no-remat and micro8 rows come last, so that the 25-minute deadline reaches the new ones). 2 warm-up and 12 timed steps of random tokens, every step ended with block_until_ready. The attention is chosen once (by the base variant, as in training) and reused by the others.
- `window512` and `muon-shard+window512` run the step with `--window 512 --window-layers auto` (sliding-window attention in three of every four layers, layers 3, 7, 11, ... and the last stay dense; the Rust trainer's rule and mask), each with `base`'s attention pick; the windowed layers use a second splash kernel that must pass the same value-and-gradient check against XLA as the dense one, else the row measures XLA attention (see its `attention` column).
- It is a different model, not only a speed option: our proxy runs found no quality loss at equal tokens (ledger rounds 13 and 15), but the TPU speed gain is unmeasured until these two rows have run; compare them with `base` and `muon-shard` in tokens per second.
- `remat-attn` (`--remat-policy dots+attn`) saves the splash kernel's output and logsumexp (about 400 MB more per chip) so that the backward pass does not run the forward kernel again, and `fuse-qkv` computes q, k and v as one matmul on `[wq; wk; wv]`: both the same numbers as `base`, speed unmeasured (`remat-attn` is `base`'s program when the attention falls back to XLA's); `hd128` is `--heads 8 --kv 2 --head-dim 128` (same parameters, heads that fill the 128-wide MXU: a speed question, the quality is another); `all` = `--muon-shard --window 512 --window-layers auto --remat-policy dots+attn --fuse-qkv` (a different model because of the window).
- Reading the result (`bench.json`, the same table at the end of `bench.log` and the notebook): rows are sorted by tokens per second, `gain` is against `base` (the training kernel as it runs now). `median s` is the step time (use it, not `min s`); `peak GiB` is the device memory peak when jax reports it (v5e has 16 GiB per chip: a `no-remat` or `micro8` row near it is risky for a 28,000 s run). `micro8` variants run 131,072 tokens per step: their tokens per second are comparable, but a bigger batch changes training (fewer, larger steps), so adopt it only on purpose. Statuses: `ok`; `oom` (out of memory, the row is a measurement of what does not fit); `error` (the message is the first 300 characters; for a flag the runtime refuses it is usually the runtime's own text, which means that flag set is not usable on this libtpu); `timeout`; `skipped` (deadline). `exit.txt` is 0 when `base` was measured.
- Adopting a result: a row clearly above `base` (a few percent is inside the noise of 12 steps; rerun it if the gain is small) becomes a flag in the settings `args` (`--muon-shard`, `--no-remat`) or `LIBTPU_INIT_ARGS` in the kernel; check the first steps of the next training session against the loss curve of the last one (the sharded Muon update is the same math per matrix, checked to match on 8 fake CPU devices, but real hardware is another thing).
